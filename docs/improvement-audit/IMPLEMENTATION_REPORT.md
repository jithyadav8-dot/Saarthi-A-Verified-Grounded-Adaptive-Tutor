## API compatibility and local persistence

A client first calls `POST /quiz` or `POST /diagnostic`. For each returned item, submit `student_id`, `q_id`, `attempt_id` and `answer` to `POST /answer`. Retry with the same exact answer and ID. Feedback includes `previous_mastery`, `new_mastery`, `mastery_reason`, `learning_opportunity` and `replayed`. The legacy ID-less request works only if exactly one issuance matches. Unissued items, cross-student mismatches and ambiguous reissues return 409. In-flight pre-upgrade questions must be requested again. After exhaustion, a new practice cycle makes the whole eligible pool available again, with a fresh attempt ID on each issuance. A regression test follows two full cycles to catch a reset that repeatedly serves only the first item.

Startup creates the attempts table and adds the chat metadata column to existing SQLite databases. Historical messages can lack metadata. There is no destructive conversion of existing learner profiles. Historical duplicate learning events cannot be reconstructed reliably and are left intact. Back up an existing local SQLite file before an upgrade if rollback is required.
